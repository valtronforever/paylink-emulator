# Verification layers

1. `cargo test --locked`: deterministic model tests and real-socket API tests. Covers state transitions, busy handling, exact amounts, timeout ties, every terminal error, setup unavailability, error recovery, control authentication, origins, idempotency, reset, isolation, listener disable/rebind, lost/partial/malformed replies and realtime client timeout.
2. `npm run test:browser`: Playwright CLI against a temporary HTTPS page and the actual payment listener. No `page.route` or mock fetch. Asserts separate operation/approval counters, manual card events, visible error text, recovery, CORS rejection and duplicate charge after a lost reply and reload. Uses OpenSSL to create a one-day local test certificate; `ignoreHTTPSErrors` trusts only the harness certificate and does not disable CORS.
3. Native GUI: build with `cargo build --locked -p paylink-gui`; exercise keypad amount, manual card/OK, bank decision, timing selection, each outcome, busy actions, reconnection, journal and reset. In attach mode use the same CLI/API test process to verify GUI events in the journal.
4. Reference differential testing is a separate gate: no real Windows/terminal captures exist yet. The compatibility report must remain unverified. Follow [calibration procedure](COMPATIBILITY.md).

Artifacts: Playwright JSON at `test-results/browser-report.json`, per-test final journal, screenshots and failed traces under `test-results/browser/`. `--journal path` exports the engine with a capture wall-clock timestamp on changes/shutdown. Monotonic event timing is deterministic. Process restart begins a fresh model; exported evidence is not automatically restored.

Browser test helpers are in `tests/browser/fixture.mjs`. Each test gets a fresh server/token/ports, `arm`, `control`, and a page already open at the HTTPS harness. A typical sequence is `arm → click → await visible result → assert counters → export`. Never share one queue among unrelated workers.

The catalog's 13 entries are **not** a complete PayLink API code list. The 11 terminal cases have synthetic model/API/browser exercise coverage. The not-running case is exercised as genuine listener unavailability; driver 9011 is setup-only. All remain unverified against the reference implementation. Inerix product UI coverage belongs to [inerix#476](https://github.com/valtronforever/inerix/issues/476) and remains pending until that integration is built.
