## Проблема

Перед реалізацією #476 потрібен власний керований емулятор **Checkbox Desktop PayLink**, щоб перевіряти інтеграцію з браузера без реальних списань. Простих статичних відповідей `success/error` недостатньо: термінал займається операцією, очікує покупця/банк, може завершити платіж після таймауту клієнта або втратити відповідь уже після списання.

Емулятор має бути окремим тестовим сервісом із двома інтерфейсами: **API сумісності PayLink для Inerix** та **керівний API для тестового runner**. Inerix використовує звичайний платіжний адаптер; тест через керівний API задає поведінку й перевіряє фактичні події незалежно від UI.

Ця задача є передумовою розробки інтеграції #476. Вона створює тестову інфраструктуру та підтверджений контракт; сама інтеграція в касовий UI виконується в #476.

## Очікувана поведінка

1. Тест запускає ізольований екземпляр емулятора, перевіряє версію профілю й отримує адреси платіжного та керівного API.
2. Керівним API налаштовує термінал, мерчанта, результат, затримки, момент помилки та спосіб доставки відповіді.
3. У браузері користувач підключає цей endpoint через «Пристрої»; конфігурація залишається в `localStorage`, як передбачено #476.
4. Платіж проходить часові етапи. Тест може чекати досягнення конкретного стану, прикласти віртуальну картку, підтвердити/скасувати дію покупця або відтворити збій.
5. Браузер отримує відповіді/мережеві наслідки, сумісні з зафіксованим PayLink. Керівний API окремо показує, чи було фактичне змодельоване списання, скільки команд надійшло й що сталося з відповіддю.
6. Кожна задокументована помилка має машинозчитуваний сценарій і параметризований тест. Повторний запуск сценарію з тими самими параметрами дає відтворюваний результат.

## Обсяг робіт

### 1. Зафіксована версія та доказ сумісності

**Ціль першого профілю: Checkbox Desktop PayLink `2.1.20`, `win-x86`.** На 21.09.2026 офіційна [інструкція](https://wiki.checkbox.ua/app/pc/portal_acquiring) посилається на [інсталятор цієї версії](https://api.checkbox.ua/update-service/api/v1/pos_srv/versions/2.1.20/win-x86/installer). Це обрана ціль сумісності, а не заява про вже перевірену поведінку її бінарного файла. Версію Checkbox cloud API та AirCheck не використовувати як версію Desktop PayLink.

- Створити незмінний профіль на кшталт `desktop-paylink-2.1.20-win-x86`; не використовувати `latest`, діапазони версій або автоматичне оновлення еталонного PayLink під час зняття контракту.
- Під час підготовки еталона зафіксувати URL, SHA-256 завантаженого інсталятора, фактичну версію/build встановленого ПЗ, дату перевірки, ОС, банк, модель/прошивку термінала, протокол і режим підтвердження. Хеш ще не визначено; обчислити з отриманого артефакту, не підставляти умовне значення. Не комітити сторонній інсталятор у репозиторій.
- Зберегти manifest профілю, специфікацію контракту, знеособлені fixtures запитів/відповідей, реєстр помилок і матрицю сумісності. Для кожного факту вказати походження: офіційний контракт, спостереження на еталоні або синтетична ін’єкція збою.
- Надана wiki не містить повного контракту локального API. До реалізації сумісного інтерфейсу отримати офіційну специфікацію/допустимі приклади або зняти обмін із еталонного PayLink. Непідтверджені HTTP-коди, поля, маршрути й гарантії не вигадувати.
- Стан профілю: `draft` до калібрування, `verified` лише після контрактного порівняння з еталоном. До `verified` дозволена розробка керівного API та моделі, але емулятор не є доказом готовності #476 до реального обладнання.
- Семантика може залежати від банку/протоколу. Для першого релізу явно перелічити перевірені комбінації; неперевірені не оголошувати сумісними. Зміна PayLink або протоколу потребує нового профілю/ревізії доказів, а не непомітної зміни старих fixtures.

### 2. Два незалежні API

**API сумісності** відтворює лише підтверджені можливості цільової версії: виявлення/перелік пристроїв, інформацію й доступність термінала, команду оплати та отримання результату; скасування, підтвердження й пошук попередньої операції — лише якщо вони існують у реальному API. Зберігати методи, URL, типи/одиниці полів, обов’язковість, регістр, заголовки, HTTP-статуси, формат помилок і синхронну/асинхронну модель відповіді. Не додавати до платіжного API зручні тестові методи, яких немає в PayLink.

- Inerix не передає `scenario_id`, штучний `run_id` або `test=true` у запиті до сумісного API. Вибір сценарію виконується тільки керівним API.
- Відтворювати поведінку повторних команд за еталоном. **Не робити емулятор автоматично ідемпотентним**, якщо PayLink не дає такої гарантії: він має виявляти повторне списання в помилковому клієнті.
- Перевіряти суми, валюту, ID термінала/мерчанта та параметри за контрактом. Результат містить узгоджені синтетичні реквізити: сума, час, ID операції, RRN, auth code, номер сліпа, маска картки та інші підтримані поля.
- Реальний мережевий listener доступний браузеру; порт конфігурований. Окремий localhost origin для UI-тестів, без reverse proxy через Django, який приховає CORS/локальні мережеві обмеження. HTTPS/HTTP, preflight і заголовки відтворюються згідно з еталонним профілем; не використовувати безумовний `Access-Control-Allow-Origin: *` для маскування несумісності.

**Керівний API** має власну OpenAPI, версію `/control/v1`, валідацію та окремий порт/listener. Наведені маршрути — проєкт нашого емулятора, не маршрути PayLink:

| Метод і маршрут | Призначення |
| --- | --- |
| `GET /control/v1/health`, `GET /control/v1/profile` | Готовність; версії емулятора/API/PayLink, hash контракту та статус калібрування. |
| `GET /control/v1/error-catalog` | Усі помилки, джерела, застосовність і спосіб відтворення. |
| `PUT /control/v1/devices/{id}` | Задати термінал, мерчантів, протокол, online/busy та інші дозволені профілем параметри. |
| `POST /control/v1/scenarios` | Створити валідований сценарій із результатом, часовими етапами й точками ін’єкції збоїв. |
| `POST /control/v1/scenario-queue` | Атомарно поставити сценарій у чергу для конкретного пристрою й команди; задати кількість застосувань. |
| `GET /control/v1/operations`, `GET /control/v1/operations/{id}` | Незалежний стан змодельованої операції, результат і лічильники. |
| `POST /control/v1/operations/{id}/events` | Подія віртуального покупця/банку/пристрою: прикладання картки, підтвердження, відмова, від’єднання — з перевіркою допустимого переходу. |
| `GET /control/v1/events?after=<cursor>&wait_ms=<n>` | Обмежене очікування наступної події без довільних sleep у тесті. |
| `PUT /control/v1/transport` | Стан платіжного listener та мережеві збої; керівний API залишається доступним. |
| `POST /control/v1/clock/advance` | Керований час у детермінованому режимі. |
| `POST /control/v1/reset` | Скидання тільки поточного ізольованого екземпляра, із завершенням/скасуванням таймерів попереднього покоління. |

Керівний API ідемпотентно обробляє повторні адміністративні команди за `command_id`, щоб retry тестового runner не додавав сценарій двічі. Це окрема гарантія нашого control API, яка не переноситься на PayLink API.

### 3. Модель термінала, станів і часу

Внутрішня модель: `idle → connecting → awaiting_card → awaiting_customer → authorizing → awaiting_confirmation (якщо потрібно) → completed`. Альтернативи: `declined`, `cancelled`, `terminal_timeout`, `reversed`, `disconnected`. Це внутрішні назви емулятора; назовні віддавати тільки реальні стани/відповіді PayLink.

- Одна активна платіжна операція на термінал. Конкурентна команда отримує підтверджений еталоном результат зайнятості; не ставити її мовчки в чергу, якщо так не працює реальний сервіс.
- Розділити **стан банківської операції**, **стан термінала** та **доставку відповіді клієнту**. `unknown` на стороні Inerix може відповідати успішному списанню всередині емулятора.
- Налаштовувати тривалість кожного етапу в мілісекундах, затримку перед відповіддю, паузи між повідомленнями й deadline. Монотонний час керує таймерами; wall clock — датами реквізитів. Зміщення годинника ПК не повинно випадково ламати всі внутрішні таймери.
- Два режими: `realtime` для справжніх затримок і `controlled` для керованих переходів. «Типові» затримки калібрувати на вимірах; до цього позначати як синтетичні. За wiki очікування термінала може завершитися через **120 секунд**; прив’язку цього таймауту до фази/протоколу уточнити на 2.1.20.
- Контрольований режим підтримує зупинку на етапі до події API та advance часу; не використовує CPU busy-wait. Він не прискорює автоматично таймери браузера чи Django. Для довгих сценаріїв явно синхронізувати тестові годинники або залишати realtime-прогін; тести границь клієнтського timeout мають перевіряти реальний таймер клієнта.
- Тестувати `T−ε`, `T`, `T+ε` щодо timeout із документованим правилом порядку одночасних подій. Jitter опційний і лише з зафіксованим seed; за замовчуванням детермінована послідовність.
- Закриття вкладки/AbortController/розрив клієнтського запиту не означають скасування платежу. Операція й таймери живуть незалежно; можливий пізній успіх, навіть якщо UI вже показує невідомий результат.
- Окремо моделювати confirmation і можливий reversal для відповідного BPOS-профілю. Не вважати проміжну авторизацію остаточним успіхом і не поширювати цей сценарій на протоколи без такого етапу.
- Snapshot сценарію фіксується на початку операції. Зміна загальної конфігурації не змінює активну операцію заднім числом; зміни через events мають журнал і перевіряються моделлю.

### 4. Каталог усіх задокументованих помилок

Початковий перелік із [офіційної сторінки помилок](https://wiki.checkbox.ua/app/pc/desktop_paylink_errors), перевіреної 21.09.2026. У таблиці `id` — наші стабільні ключі, а не коди PayLink. Точні wire-відповіді й канали прояву заповнити за профілем 2.1.20.

| Власний `error_id` | Задокументований випадок |
| --- | --- |
| `paylink_not_running` | Desktop PayLink не запущено. |
| `terminal_unknown_0` | `ErrorCode=0`, невідома помилка термінала. |
| `terminal_general` | `General error`. |
| `merchant_profile_invalid` | Неправильний профіль продавця. |
| `host_clock_invalid` | Помилка `rr` через час ПК. |
| `bank_host_unreachable` | `No connection with host`. |
| `customer_cancelled` | `Transaction canceled by user`. |
| `terminal_connection_refused` | З’єднання з терміналом не встановлено. |
| `terminal_busy` | `Device is busy`. |
| `terminal_timeout` | `Timed out`. |
| `terminal_id_invalid` | Невідповідний ID термінала. |
| `verification_fault` | `Verification fault`. |
| `driver_install_9011` | Помилка встановлення драйвера `9011`. |

- Для **кожного** запису: source URL/розділ/дата та версія snapshot, applicable profile/protocol, фаза, передумови, фінальний банківський ефект, видимий клієнту результат, можливість відновлення, fixture, scenario ID та test ID. Каталог розширюється всіма додатковими помилками отриманої локальної API-специфікації; наведені 13 випадків не оголошувати повним переліком API-кодів.
- Розрізняти помилку бізнес-операції, відповідь сервісу й транспортну несправність. Вимкнений PayLink має давати реальну недоступність платіжного listener, а не умовний JSON `500`. Помилка з’єднання PayLink → термінал може мати іншу API-поведінку, ніж недоступність браузер → PayLink.
- `9011` належить до встановлення драйвера. Через control API відтворювати її клієнтсько-видимий наслідок, встановлений на еталоні (наприклад, недоступний пристрій, якщо це підтвердиться). Не приписувати коду вигадану HTTP-відповідь оплати. Якщо помилка не спостерігається через клієнтський API, позначити `setup_only`, документувати причину та перевірку інфраструктурного наслідку; не рахувати це як перевірку показу конкретного коду в UI.
- Для ще непідтвердженого випадку ставити `unverified`, із явним блокуванням заяви про повне покриття. Не замінювати всі коди одним generic error і не пропускати їх через `skip` без відображення в звіті.
- Звіт покриття показує кожну помилку: `verified/pass`, `failed`, `unverified/blocked`, `setup_only`; повнота перевіряється машинно за каталогом, а не вручну написаним відсотком.

### 5. Додаткові сценарії надійності та керування поведінкою

Ці сценарії — тестові ін’єкції, окремо від офіційного каталогу помилок:

- Успіх, банківська відмова, скасування до/під час авторизації згідно з дозволеними переходами.
- Операція успішна, але відповідь втрачена; відповідь прийшла після клієнтського timeout; повторна доставка, якщо транспорт підтримує повідомлення.
- Два конкурентні платежі; повтор команди під час зайнятості та після завершення; неправильний термінал/мерчант/сума.
- Зависання без відповіді, розрив TCP до обробки, після прийняття, після банківського результату та посеред response body. Фактичний розрив не замінювати звичайною JSON-помилкою.
- Некоректний JSON/Content-Type, неповний payload, невідомий код, нестача реквізитів, HTTP 4xx/5xx — позначити як synthetic, якщо не задокументовано еталоном.
- Окремий транспортний профіль для CORS/preflight та мережевих дозволів браузера. Помилки дозволів тестуються справжнім браузером, а не вигаданим кодом PayLink.
- Перезапуск/від’єднання пристрою, restart сервісу та відновлення — зі збереженням або втратою стану саме за профілем. Задокументувати, які гарантії ще не підтверджено.

Сценарій задає `device_id`, операцію, кількість застосувань, внутрішній outcome/error ID, фазові затримки, події покупця та політику доставки відповіді. Операції мають точний matcher (включно з сумою/мерчантом, якщо задано), атомарне споживання сценарію та зафіксоване правило його споживання щодо validation/busy. Невикористані й несподівані команди відображаються в assertions. У strict test mode відсутній сценарій — помилка тесту без симуляції успішної оплати; цей захист відділений від поведінки сумісності PayLink.

Приклад **нашого керівного сценарію**, формат ще належить реалізувати; це не запит реального PayLink:

```json
{
  "profile": "desktop-paylink-2.1.20-win-x86",
  "device_id": "terminal-1",
  "operation": "purchase",
  "uses": 1,
  "timing": {
    "connect_ms": 300,
    "await_card_ms": 2000,
    "authorize_ms": 1200
  },
  "outcome": {"type": "approved"},
  "response_delivery": {"type": "disconnect_after_commit"},
  "seed": 42
}
```

Наведені мілісекунди — синтетичні параметри тесту. Для будь-якої помилки аналогічно передається її `error_id`; помилка, фаза й платіжний ефект мають бути сумісними. Control API відхиляє неможливі поєднання, а не приховано нормалізує їх.

### 6. Журнал, ізоляція й запуск у CI

- Структурований журнал із порядковим номером, correlation/operation ID, пристроєм, профілем, scenario ID, отриманою командою, переходами, монотонним і календарним часом, змодельованим банківським ефектом та доставкою відповіді.
- Окремі лічильники: отримані payment requests, прийняті terminal operations, approvals/списання, reversals і доставлені результати. Тест перевіряє «одне списання», а не просто одну HTTP-відповідь.
- Стан не залежить від сторінки чи localStorage браузера. Журнал доступний після reload та експортується після тесту. Перезапуск процесу має явну політику профілю; доказовий журнал зберігається поза життєвим циклом платіжного listener.
- Один процес/набір портів/стан на Playwright worker або тест. Не змінювати реальний API додатковими тестовими headers для ізоляції. Reset гасить активні timers/connections, змінює generation ID; пізні події старого тесту не впливають на новий.
- Запуск локально та в CI однією документованою командою, readiness, конфігуровані порти, коректне завершення, ненульовий exit code при невдалих assertions. Сервіс має працювати без production БД, мережі банку та встановленого PayLink на CI; Windows потрібен для еталонного калібрування.
- Control API доступний тільки тестовому runner: окремий loopback listener і run-scoped token; токен не передавати браузерному коду Inerix. Для контейнерного режиму — закрита тестова мережа з явною конфігурацією доступу. Емулятор не входить до production deployment і не має passthrough до банку/реального термінала.
- Усі реквізити синтетичні. Санітизувати еталонні записи; не включати PIN, токени Checkbox, cookies або повні карткові дані в fixtures/артефакти.

### 7. Перевірки та межа із задачею #476

Пропоновані ділянки: окремий каталог `tools/paylink-emulator/` для сервісу, профілю й contract tests; `frontend/tests/e2e/` для fixtures керування й smoke-тесту браузерного транспорту; окремий README та OpenAPI control API. Шляхи нові й можуть бути уточнені при реалізації. Використати наявні `frontend/playwright.config.ts`, npm script `test:e2e` та приклади `frontend/tests/e2e/devices-label-printer.spec.ts`.

У цій задачі виконати:

1. Unit-тести моделі станів, clock, сценаріїв, конкурентності, журналу та reset.
2. Contract/differential tests: ті самі безпечні запити проти еталонного PayLink 2.1.20 і емулятора, із нормалізацією лише змінних ID/часу; порівняння схем, помилок, послідовності й виміряних часових допусків. Немає одного універсального результату для всіх банків.
3. Параметризований тест кожного error-catalog запису й кожного transport fault через API; перевірка наступного відновлення після помилки.
4. Headless Playwright CLI smoke з окремою тестовою HTTPS-сторінкою, що використовує той самий wire-контракт: listener, CORS, real-time очікування, справжній розрив, стан після reload. Це технічний harness без окремого продуктового UI. Не використовувати `page.route()` для перехоплення емулятора в тестах його транспорту.
5. Готові Playwright helpers для `configure → arm scenario → act in browser → await event → assert journal → export/reset`, приклади і expected outcomes для майбутніх UI-тестів #476. Автоматичний coverage report зі зв’язком помилка → сценарій → contract/API test → UI test.

У #476 після появи UI виконати ту саму матрицю через справжнє меню «Пристрої» та чек Inerix: налаштування localStorage, вимкнений режим без запитів, карткова/змішана оплата, кожна клієнтсько-видима помилка, loaders, recovery, дві вкладки, повторна команда, помилка Checkbox після списання та помилка локального завершення. До цього UI coverage позначений pending, а не pass. Емулятор не підміняє Django-сервіси завершення та окремий Checkbox fiscal API; помилки останнього задаються backend-стабом.

**Не входить:** банківський процесинг/EMV/криптографія, робота з реальними картками, емуляція драйверів ОС, автоматизація повернень, продуктова адмінпанель емулятора, реалізація #476 або гарантія сумісності з усіма версіями/банками. Фінальний прогін #476 на реальному обладнанні залишається необхідним.

## Критерії приймання

- [ ] Профіль зафіксований на **Desktop PayLink 2.1.20 win-x86**; manifest містить перевірений hash інсталятора, build, contract revision і перелік перевірених банків/протоколів. Немає автоматичного переходу на іншу версію.
- [ ] Локальний API-контракт підтверджено джерелами/еталонними трасами. Задокументовані прогалини не представлені як сумісні реалізовані методи; готовність `verified` вимагає контрактного порівняння.
- [ ] Inerix-клієнт може замінити лише endpoint на емулятор без спеціальних тестових полів чи окремої платіжної логіки.
- [ ] Через control API задаються успіх і кожна помилка каталогу, часові етапи, точка збою та доставка відповіді; не потрібне ручне редагування файлів/перезапуск для вибору наступного сценарію.
- [ ] Усі 13 випадків із поточної wiki й додаткові помилки отриманого API-контракту мають записи з доказом застосовності, сценаріями та тестами. `setup_only` пояснено й перевірено через доступний клієнту наслідок; `unverified` не зараховано в успішне покриття.
- [ ] Є реальні затримки, busy під час активного платежу та контрольований час. Перевірено границі timeout і окремий realtime-прогін 120-секундного сценарію, якщо він підтверджений цільовим профілем.
- [ ] «Успіх усередині термінала → втрачена відповідь → reload → повторний запит» відтворюється незалежно від UI. Журнал дозволяє встановити, чи клієнт допустив дубль списання.
- [ ] Емулятор не додає ідемпотентності, status lookup чи автоматичного скасування, яких немає в еталоні. Confirmation/reversal застосовуються лише до підтверджених профілів.
- [ ] Транспортні збої є справжніми мережевими наслідками; платіжний listener можна зупинити через control API, зберігши доступ до керування/журналу.
- [ ] Control API залишається чутливим до запитів при тривалому платежі; invalid event/config відхиляється, повтор control-команди не дублює сценарій.
- [ ] Паралельні workers ізольовані; reset/teardown прибирають таймери та не допускають пізніх подій між тестами. Seed, профіль і параметри відтворюють сценарій.
- [ ] Є unit, contract/API та браузерні transport-тести, Playwright helpers і machine-readable coverage report. У звіті чесно відокремлено готовність емулятора від ще не виконаних продуктових UI-тестів #476.
- [ ] Saved artifacts: знеособлені fixtures, журнал подій, counters, traces/screenshots/JSON CLI Playwright і timing/compatibility report. Є інструкція запуску, API приклади, калібрування, додавання нової помилки та нового версійного профілю.
- [ ] Емулятор не може провести справжній платіж; control API недоступний production UI; артефакти не містять секретів або реальних карткових даних.
